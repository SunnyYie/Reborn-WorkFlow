# 三首敬拜歌单 Workflow

先阅读 [运行与 JSON 接口](README.md)。引擎不调用独立模型；主题理解、推荐和自然语言问答由当前 Codex 完成。不要把引擎说成能独立理解主题的自动选歌算法。

## 先查已有编排

任何 PCO 查询、下载和音频结构分析前，先读 [历史歌单 RAG](../rag/SKILL.md)，对用户偏好/候选歌名查询本地库。命中且版本选定、资料完整时，保留主题/方案/歌序确认，**跳过该首文档下载、简谱识别与音频结构分析**。完整流程仍完成本次定调试听、MP3 交付和话语确认；历史调不自动适合本次歌手。仅本地快速组装且不需要定调/MP3 时才可省略这些音频环节。存量疑点仅核对相关原件，未命中的歌曲才获取缺失资料。

需要完整定调、话语与组装时，在同一会话用 `rag-search` 留检索记录；PCO inspect 核验真实歌曲与现有调身份。定歌后用 `material-prepare` 绑定选定 RAG main 记录和版本依据，resources/download 自动跳过这些文档，只下载缺失歌曲资料和已确认调 MP3。全局库不变，会话材料库单独保存；不得伪造 PCO ID、试听或下载结果。仅需要本地文档、不需要 PCO 定调时仍可直接走 `rag/run assemble` 的快速分支。

## 执行节奏与当前状态

- 每次续接先 `status`，需要完整证据时再 `show`；阶段、确认、有效材料和当前成品以CLI为准，不把历史报告里的“待确认”恢复成当前缺项。报告只维护一个当前状态入口，其他文档明确为阶段快照。
- 对多版本一次展示来源、歌词乐段、完整路径、各间奏位置/小节与疑点，并给有依据的推荐；不能只说“资料待选择”。`recommended_id`只表示唯一无疑点候选，不代替用户选版本。用户已指定或唯一可确定的直接绑定，不再追问。
- 关键缺项集中询问，已确认的保持不变；局部修改只重新核对受影响部分。定歌、试听、话语、整份组装的确认仍分开，不把“继续”当新稿获批。
- 仅补证据或确认记录且正文不变，不生成新Word。相同请求重复导出使用`--reuse-existing`，以返回的实际路径为准；参数有变化时先比较是否影响正文，不为revision变化机械增加副本。
- 成品展示规则在首次导出前明确：活动日期/人员等是来源元数据，默认不进入正文；明确需要时用`presentation.show_event_metadata=true`。不在正式稿添加内部“待审”“人员待定”等过程说明。

## 第一段：定歌、定调与资源准备

1. `new` 创建会话，保存返回的 `state_path`。继续既有会话时先 `show`，不另起会话丢失反馈。
2. 收集总主题、需要的生命叙事或回应、第 1/2/3 首的快/慢/不限；已知信息直接写入 `requirements`，仅问缺失项。不把旧会话的歌单或快慢要求默认带入新会话。
3. 明确问是否有倾向歌曲；没有也写 `preferences: []`。默认是偏好，只有用户明确必选才设 `mode: required`；必选冲突先询问调整，不擅自放宽。歌名歧义先用查询结果让用户确认，必选曲必须解析为真实 ID。
4. 读取 [搜索 skill](../skills/search/pco-search-songs/SKILL.md)，使用 `doctor`、`catalog`、`inspect` 查询真实库。`catalog` 是标题/目录查询，不是歌词语义检索，也不等于查遍全库编曲。`inspect` 输出当前歌词供本轮阅读，但状态只保留是否有歌词与哈希，不留全文。
5. 读取 [歌单规划 skill](../skills/pco-plan-worship-set/SKILL.md)。默认**最多三套**，只给符合条件且有实质差异的方案；一套或两套合适就只给一套或两套。不为填满数量生成弱匹配或近似组合。
6. 每套恰好三首，给整体方向、各首选择原因、位置原因、完整排序原因和取舍，并指出优先推荐。尽量保留偏好的方案与主题更贴合的替换方案可对照；没有偏好时不硬设“保留原歌”方案。`propose` 提交后展示给用户，引用返回的当前 `revision`，不自行确认。
7. 用户不满意：先问具体要优化主题、歌曲、顺序、快慢或其他哪部分；取得具体反馈后调用 `feedback`，必要时更新 `requirements`，再检索、再推荐。信息不足以生成任何合格方案时说明缺口并询问放宽条件，不提交空方案。
8. 用户明确确认具体歌单及顺序，才调用 `confirm`。有未知项时先披露，获得接受后才能设置 `accept_unknowns: true`。`user_message` 引用或忠实记录真实用户确认，禁止伪造、把“看看 A”当确认，或将实施本 workflow 的授权当作确认歌单。
9. 读取 [定调 skill](../skills/pco-select-song-keys/SKILL.md)，收集男、女歌手人数，各组属于低/中/高音；用户已说的不要重复问。通过 `key-requirements` 保存，分组人数必须与男女总数相符。可询问舒适音域、每首主领以改善判断，但不要强制要求用户具备乐理知识。
10. `key-options` 读取已定编曲的现有 Key，继续读取单个 Key 详情给出的附件链接，按真实 Key 关联 MP3。Key 列表本身可能不显示附件链接；不能把同歌另一调的 MP3 或只有“可下载 MP3”标志的 PDF 当音频。失败项、没有匹配附件与权限受限分开说明。
11. 用实际库内调生成 `key-propose`：每首选用调、对应 MP3、建议主领组、选调理由、音域证据和风险。通常一套优先方案，必要时给少量有实质差异的备选，不凑数。不要用“男声固定某调/女声固定某调”代替音乐判断；没有旋律和舒适音域实证时明确只是待试唱推荐。
12. `key-preview` 按指定方案临时取得三首对应调的原始 MP3，输出可播放的实际本地文件；向用户说明仅是试听缓存，尚未正式归档，也没有下载歌词。展示音频时按平台支持使用绝对路径的音频嵌入。代码记录 prepared 不代表用户 listened。
13. 用户听完三首并明确表示没问题，才 `key-confirm`（使用 `keys.revision`，`listened: true` 必须来自真实反馈）。用户觉得高/低或不舒服，用 `key-feedback`，必要时调整歌手信息，再推荐、试听、确认。不能将歌单确认当成定调确认。
14. 定调确认后按 [下载 skill](../skills/download/pco-download-chinese-lyrics/SKILL.md) 调用 `resources` 和一次 `download`：统一交付每首已听过的对应调 MP3，以及现成中文歌词或回退简谱。没有歌词/简谱则报告文档缺失，不建文档占位文件，但仍交付已授权 MP3。优先复用试听缓存，不重复获取同一音频。环境权限仍按系统要求申请。

## 第二段：定祷告与话语

1. 第一段定歌和 `key-confirm` 成功、已执行资源准备后进入本段，读取 [祷告话语 skill](../skills/pco-plan-spoken-transitions/SKILL.md)。下载结果中的缺失/失败如实说明，不把资源齐全当作已验证条件；歌词依据不足时先补充核验或询问用户，不凭标题写成强关联。
2. 读取已确认的主题、实际三首歌及顺序、歌词证据，询问话语位置、形式、时长、语气和经文译本中尚缺且会影响内容的信息。不要重复问已有信息，也不悄悄改歌。
3. 调用 `spoken-requirements`。当前默认四处：第一首间奏祷告、第二首前奏开始前话语、第三首前奏开始前话语、第三首间奏话语。位置可按本次用户要求修改；默认《和合本》并告知用户可换译本，未知间奏长度保持未知。
   写稿前必须`spoken-context`读取已绑定资料的具体器乐段。新话语要求遇到已知小节时，以`route_index`和`material_fingerprint`绑定位置；有参考速度时填写`window`，明确BPM拍点的`beats_per_bar`、留白和`tempo_basis`，先算容量再写稿。参考速度不是本次乐手BPM；拍点无法核对时用`timing_unknown_reason`并逐处披露，不能伪造参数。覆盖历史小节需`bar_override_basis`记录本次用户/乐手依据，详见README。
4. 根据对应歌曲内容生成 `spoken-propose` 草稿；第二、三首前的话语保留与上一首核心表达的联系，不机械复述歌名/歌词。结尾只表达将要唱的内容，不说“接下来唱《歌名》”。“让我”等普通词语不因也是歌名就禁用。
5. 第一首间奏以回应本首为主，可为后续铺垫但不能当作本首结束；第三首间奏深化本首委身回应，不虚构第四首。每处只给一份完整口述稿，不套用“最多三套歌单”的数量规则。
6. 经文记录章节、译本、引用方式和核对来源。逐字引文必须保持原文，不将祷告或意译冒充经文；无可靠原文时可标待核对写草稿，但经文未核对不得定稿。代码只校验记录和一致性，助手必须实际核验来源，不能伪造核验标记。
7. 展示四处完整内容、关联理由、经文出处和估计时长，收集意见。用户修改话语用 `spoken-feedback`，修改位置/时长/译本用 `spoken-requirements`，再 `spoken-propose`；不调用第一段 `feedback`，避免无意取消定歌。
8. 用户明确确认整份话语稿后才 `spoken-confirm`（使用 `spoken.revision`，不是顶层歌单 revision），再 `spoken-export` 导出现场稿。确认了歌单不等于确认话语；任何话语修改均撤销旧话语确认。
9. 若用户要求换歌、换顺序、换调或调整歌手配置，回到第一段对应环节；第二段旧稿会自动标为 `stale`，不得套用或导出，需按新定歌/定调重新生成并确认。只改话语不影响已定歌曲和调。

顶层 `stage` 表示第一段进度，定调另有 `keys.stage/revision/confirmation`，第二段独立放在 `spoken.stage`。旧会话已确认的歌单可以保留，但不能绕过新增定调；补齐定调试听确认后再下载或进入第二段。

## 第三段：完整歌单组装

1. 定歌后先绑定 RAG 命中资料；下载后将未命中的原始中文 TXT/DOCX 用 `material-prepare` 整理为原文分段和有依据的结构。参考 [接口与输入格式](README.md)。谱面/PDF 必须先完成组装阶段核验，才能通过带源哈希、逐段/逐次页码或音频时间证据、无未解疑点和明确确认的 `analysis` 导入；接口不自动转录或理解音乐。
2. 完成第二段话语确认后，询问回应与结束歌曲，读取 [组装 Skill](../skills/pco-assemble-worship-setlist/SKILL.md)。补齐三首经文，实际核对原文并记录译本、章节、来源与核验方式。
3. `setlist-propose` 提交有序三首经文及回应/结束。当前调从已试听确认 Key 派生，BPM 只采用本次乐手值，无值空白。结束先查 RAG，覆盖已有 V/C/B/PC 等；无 LL 不加 LL，派生结构不冒充历史原表。
4. `setlist-export --draft --output ...` 生成待审稿；展示五位置结构、经文和四处话语，WPS 检查颜色、表格、中文和分页。让用户核对编排、来源版本、经文和现场信息。
5. 用户明确认可本次整份歌单后才 `setlist-confirm`，revision 使用 `setlist.revision`，再 `setlist-export`。导出带 `.sources.json`。歌序、调、话语、材料或结束记录改变后，重新提案确认。
6. 自动化回归可用显式 `--test-run` 的隔离会话和 `live_scenario.py`。模拟确认必须清楚标为测试，导出结果为 test_artifact；不得将测试的 listened、确认文本或歌手配置复用于正式场次。

回应新增曲目或换调时先走 README 中 `response-options/preview/confirm` 的独立试听交付；新歌资料仍先 RAG，未命中才 `response-resources` 与 `material-prepare`。不能只填写调名绕过试听。改变回应结构须传 `route` 和依据，不写“结构一致”。完整组装入口会复查三首正式 MP3 字节与试听一致；只确认调但未交付时不能组装。

本次聚会信息用 `event`，本次逐次分工/小节/强弱用 `route[].current_cue`，均记录实际来源，不复制历史分工。新版通过真实视觉检查后立即`artifact-finalize`，同一次执行登记验收、替代旧稿、预演及apply清理，不等用户再提醒。仅保留一个当前最终DOCX及sources；制作/验收期间可临时留中间稿。不得把自动化测试确认当成真人反馈。

导出与收尾必须执行 [组装 Skill 的输出与验收规则](../skills/pco-assemble-worship-setlist/SKILL.md#输出与验收)：导出器直接沿用保留模板，使用真实双栏分节和模板字体、配色、页面与页眉，不从空白文档重建。最终成果生成且 WPS 逐页检查通过后，按本次创建文件清单删除明确废弃的临时、中间版本；不只归档堆积。保留最终 DOCX、sources、必要报告、原始资料、会话状态、RAG 数据及仍被引用的缓存；失败或未验收先保留诊断证据，删除须遵守环境权限。

新`artifact-finalize`接收完整逐页及三首视觉观察与`cleanup.checked_files`（待删文件逐个路径、哈希、`closed:true`及实际说明）；已登记的同哈希验收可显式`use_existing_review:true`复用。代码先全批预检，文件仍打开、改过、有效引用或检查缺项时不删；原生观察真实性仍由执行者负责。新正式稿`required_cleanup_version=1`，仅验收或手动删除不能使交付完成，已验收但未收尾也禁止继续导出。收尾必须`status`核对`finalization_valid=true`和`cleanup_remaining=[]`；失败报告阻塞，不能伪称完成。低层`artifact-review/retire/cleanup`保留兼容，接口见README。`delivery_complete`不代表现场排练通过。

组装后的[样式与分页验收](../skills/pco-assemble-worship-setlist/references/layout-acceptance.md)为强制门禁：前三首独立起页、每页只属一首主歌，歌词优先同页；回应与结束合放新独立页，口述附录另起。v5验收逐首核对字体/字号/颜色/间距/表格宽高与实际页码，并检查共用左边界、表格到歌词留白、主歌表格宽度协调、Verse之间及Chorus/Bridge等相邻乐段12pt留白；歌词跨页必须说明原因及调整。新稿required_review_version=5，旧验收不能使其通过交付或清理；锁屏/应用不可用时只报告待验收，不自动填通过。

## 证据与异常

- 每首记录真实编曲、BPM、拍号；快慢判断由助手结合拍号与版本解释。不将 6/8 和 4/4 数字直接比较，未知不能伪造为快或慢。引擎只校验判断与逐位置要求的一致性，不代替音乐判断。
- `evidence_kind` 必须区分当前歌词、历史来源、通行版本认识、仅标题初筛。只有标题证据不足以推荐；继续核验或明确缺口。歌词字段空不意味着没有中文附件。
- `unknowns` 如实列出中文版本、未试听/柔和程度、调性或音域衔接等与本轮相关的未知。不要为了通过确认校验隐藏未知项。
- 三套的实际差异与主题匹配由助手负责；代码能拒绝重复歌序，但不能证明音乐或神学判断正确。
- `needs_review` 时查看 `resources`：含混文件不能靠猜测分类；使用已有元数据、原始来源记录或询问用户。禁止为了判断而批量试下载、OCR 或人工转录。
- 用 `review-resources` 记录有依据的附件分类；有多个资源或其他编曲版本时须记录用户选择。不能把中文歌词改标“other”来强行下载简谱。
- 确认后 PCO 编曲变化：重新 `inspect`、推荐/确认，不以重试绕过旧版本保护。需求、方案或具体反馈变化后旧确认自动失效。
- 网络、权限、受限下载、歧义与确实缺失分别报告。不将异常视为资源不存在，不自动替换已确认歌曲。
- 输出每首文档与 MP3 的独立状态。简谱只交付原件，不生成歌词 TXT；不同 Key 的谱不冒充目标调，未标调的简谱明确标“调性未核验”。文档不存在不影响已批准 MP3 的交付，可重试部分失败，成功文件不重复下载。

## 安全边界

不写 PCO 歌单、排班或歌曲内容；音频仅限本流程授权的现成对应调 MP3 试听与交付，不移调、不合成、不转码，不下载其他音视频或英文歌词。不改全局配置。凭据仅由已有环境变量或 macOS Keychain 在进程内读取，不让用户在聊天粘贴 Secret。

本 skill 位于项目目录，未全局安装。使用者可以在对话中指定先读取本文件来启动流程。
