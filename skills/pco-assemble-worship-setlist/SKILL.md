# 组装敬拜歌单

**Mini 入口例外**：用户启动 [mini-workflow](../../mini-workflow/SKILL.md) 时，以其规则为准：只查 PCO，不查 RAG、不定调、不下载音频、不强制话语/整份确认；调与BPM始终空白，未提供经文、回应及结束歌曲也留空。仍沿用本模板和真实原生版式检查；mini 空槽位验收使用明确 N/A 观察。下文完整流程及独立 RAG 组装的必填与确认规则不因此改变。

先读 [模板规则与证据](references/template-rules.md)，以用户本次要求优先。参考模板位于 `assets/reference.docx`。它是格式样本，不是固定曲目、调、BPM、演唱分工或圣经内容。需要从简谱/音频补结构时读 [结构识别与确认](references/structure-analysis.md)。

每次组装后必须执行[强制样式与分页验收](references/layout-acceptance.md)：前三首分页隔离、歌词优先整首一页、回应与结束合放独立页；逐首检查字体、字号、颜色、间距、表格样式及尺寸。代码结构检查与原生WPS/Word逐页观察缺一不可，未通过不能报告完成或清理唯一已验收稿。

本 skill 可独立运行，也已通过 `workflow/` 的 `material-prepare`、`setlist-propose`、`setlist-confirm`、`setlist-export` 接入同一会话。完整流程按 workflow/SKILL.md 执行，独立组装仍不伪造状态。使用 WPS 时加载本机 `wps-word`，文档跨应用管理按需加载 `wps-office`；其通用排版建议不得覆盖本歌单模板。安装 skill 不等于 WPS MCP 已连接，先核实实际可用接口；没有 MCP 时可用 WPS 原生界面查看。

当前导入、回应独立定调和清理命令见 [workflow 接口](../../workflow/README.md)。已核验简谱用 `material-prepare.analysis` 保存逐段/逐次页码或真实音频时间证据与原件哈希；未确认或有疑点不进入完整组装。换调/新增回应先独立试听交付，不能凭字符串覆盖调；本次结构用 `route`、`structure_basis` 和 `current_cue`。WPS实际验收并核对待删文件关闭状态后立即`artifact-finalize`，同次记录验收、替代和清理旧稿，不等另行提醒；预览只登记在会话`render-cache/`。旧低层命令保留兼容，不能绕过新正式稿收尾门禁或破坏溯源。

## 输入核对

**先查历史库**：读取 [历史歌单 RAG](../../rag/SKILL.md)，按本次歌名及用途检索具体编排记录。精确命中且结构歌词完整时直接复用，跳过下面“先分析”中的下载/谱面识别/音频分析；同名多版本先选版本，存量疑点仅核对相关位置。不把历史 BPM、调、分工或话语当作本次确认。库内未命中或实际缺失的部分才走原流程。`../../rag/run assemble` 可直接拼接五位置草稿并附来源清单，之后按本 skill 检查 WPS 版式和本次信息。

- 三首主歌的已确认歌序、曲目及编曲身份、已确认调、可用中文歌词来源。
- 每首使用的经文与译本、实际核对来源；可复用已确认话语稿里的相关经文，不把整段祷告自动填进经文栏。
- 歌词、谱面、对应音频及乐手提供的结构顺序、乐段编号、小节数；分工、强弱及读经/祷告提示由用户或乐手决定，不从男女数量或录音人声推断。
- 回应诗歌和结束诗歌的身份，以及本次是否有不同的调或结构；未指定时询问，不默认从前三首替用户决定。
- 聚会日期、名称、人员图例等页眉信息按需补充，未提供不沿用模板中的旧日期和人名。

活动元数据与成品正文分开：`event`保留来源，默认不显示开头三行；只有明确需要时设置`presentation.show_event_metadata=true`。首次导出前集中确认显示规则，不把内部状态、待审标题、人员待定说明自动加入正式稿。不要为补确认依据或revision变化重复导出；完全相同的请求用`setlist-export --reuse-existing`复用未改动成品，尊重返回路径，draft不复用为正式版。

已确认的资料不重复问。关键缺项集中询问；可以先做明确标注的草稿，但不能把缺歌词、缺经文或未确认结构的版本宣称为完整定稿。

## 先分析，再组装

从 workflow 的实际输出清单或用户给定本地文件读取资料，不仅按文件名匹配。独立使用时不创建伪 workflow 状态、不调用下载命令绕过定调确认。先核对歌曲、编曲、版本与来源，尤其分清同歌多个 MP3、原调录音和已确认调。

分开维护三层：谱面/歌词中的乐段，参考音频的实际演唱路径，用户确认的现场编排。歌词已有标签或结构表时优先提取；仅列 Verse/Chorus 不等于已给出完整顺序。简谱允许识别歌词、拍号、小节、反复、房子和明确标签；音频用于核对顺序、重复及谱面未写出的器乐段。

每次乐段出现分别记录类型、编号、对应歌词、音频起止、小节数和证据。文档已标注、谱面读取、音频推断、用户决定分开标记。不能仅用响度判断 Chorus、仅凭剩下一段命名 Bridge，或把未知数凑成常见的 4/8/16 小节。缺能力/版本不匹配时明确未验证，不能把 ffprobe 时长或波形检查称为听懂歌曲。

先给结构预览及疑点，收集现场编排修改，确认后再定稿。用户要求直接组装但结构尚未确认时可以交付待确认草稿，不伪造确认；已确认的歌序和回应选择不用重新询问。更换音频版本后撤销依赖它的顺序、小节及时间结论，歌词身份不因换调自动变化。

## 整体结构

完整歌单按五个位置排列：主歌一、主歌二、主歌三、回应诗歌、结束诗歌。五个位置不要求五首不同歌曲。

前三首各依次展示：

1. 标题：序号、歌名、已知拍号、已确认调、`BPM=`。
2. `【经文】`：核验过的经文原文、章节、译本。
3. `结构分配：`：按演唱时间顺序排列的结构表。
4. 歌词：按 Verse、Chorus、Bridge 等实际乐段组织，标记与歌词颜色对应。

标题示意：`1. 歌名 4/4 F调 BPM=`。未知拍号不得填成 4/4，未定调不得套用原调。**BPM 默认值为空**，只在乐手明确提供本次数值后填写；PCO、音频分析和旧模板里的 BPM 不能自动带入正式标题。

## 结构分配与颜色

使用两行横向结构表：上排为乐段标记，下排为同一乐段的演唱分工、小节数或现场提示。保留重复出现的乐段，不能去重。过长时按演唱顺序拆成连续表段，不挤成无法辨认的小字。

支持 IN、V/Verse、PC/Pre-Chorus、C/Chorus、B/Bridge、Tag、LL、End 及编号变体。用户写的 `Chorue` 可在内部对应 Chorus；展示沿用乐手约定或经用户同意统一，不擅改有实际含义的乐段名。

用户已明确统一器乐标记：导出时 `IN`、`INT`、`Ins`、`Int` 一律显示为 `IN`，结构表及现场提示一致；不合并段落，不改变位置或小节数，历史原件与来源记录保留原写法。

本团队 LL 通常是从 Chorus 结尾抽出一句或两句单独演唱/重复；Tag 通常是 LL 后独立的收尾内容，多数歌曲没有 Tag。副歌末句在整段副歌里正常出现不自动成为独立 LL；纯器乐尾奏不自动成为 Tag。不要把别的团队对 LL/Tag 的定义覆盖本约定，也不要为满足结束默认结构而宣称参考音频已有 LL。

按参考中的蓝、橙、绿和中性色系建立单一颜色映射，详见参考表。同一乐段的结构标记文字、歌词段标题及正文使用同一个明确 RGB；结构表可用该色系的浅底色辅助识别。区分文字色与单元格底色，不把浅色背景当正文色。模板有近似色和漏填色，不逐个复刻这些差异。

同组编号共享颜色但保持身份：V1/V2 不能互换，C1/C2 不能因相似就合并。没有实际歌词的 IN/End 不虚构歌词；有歌词的 LL/Tag 仍须有对应正文与同色标记。新乐段不随意分配冲突颜色，需要时与用户确认。

歌词正文按乐段列一次，重复次数由结构表表达；用户明确要求逐次演唱展开时再展开。不改词、不补词、不自行翻译。允许使用用户直接提供的模板歌词，但必须对应同一首及版本，不能把它当成从 PCO 下载的新证据。

用户已明确授权：**下载阶段仍只取原件；组装阶段允许识别简谱中的歌词与音乐结构**，包括图像阅读/OCR 后逐处核对。低清字、简繁差异、音符遮挡或版本冲突记录到疑点清单，不能以语感补齐。保留原谱作为依据，不把识别稿标成 PCO 原生文字。不改变已有下载 skill 或 workflow 的“不转录下载”规则。

## 回应诗歌

- 是前三首之一，且本次结构相同：保留回应标题，复制对应结构表，或写 `结构一致`。优先注明对应第几首，避免同名版本歧义，无需重复整份经文及歌词。
- 是前三首之一但回应唱法有变化：展示新的实际结构，不写 `结构一致`；调变化也必须明确，不默认为已获原定调确认。
- 不是前三首之一：按完整单首格式展示标题、经文、结构分配和歌词，不能仅写 `结构一致`。不能因为旧模板曾这么写就省略。

## 结束诗歌

展示结束诗歌名称并粘贴结构，通常不重复完整经文及歌词。乐手给定结构时原样保留顺序与编号，正确着色；发现所指乐段与歌曲不符时先核对，不能静默换成另一首的结构。

**先按歌名/别名查询 RAG 的 ending 用途**，用 `rag/run ending "歌名" --main-id 本次完整歌词版本ID` 检查。结束编排必须覆盖这首歌已有歌词的乐段类型：有 Verse、Chorus、Bridge 就都包含，有 Pre-Chorus 等也不能漏掉；编号变体不要求每次全部重复，但须能对应具体歌词。历史结束表不足时保留原文并指出缺段，再生成标明来源的本次调整，不把旧表默认为合格。

废止固定 `IN+Verse+Chorus+LL` 默认。**没有明确独立 LL 就不添加 LL，也不从 Chorus 末句自动抽出新 LL；Tag 同理。** 无可直接复用结束表时，按已有歌词段提出结构，顺序/重复/器乐小节待确认。历史结束编排与按用户规则派生的结束方案分开入库，后者不得标成原文已有结束或用户已定稿。

## 输出与验收

### 导出器必须沿用模板

以 `assets/reference.docx` 为版式依据，直接复制模板包并替换本次内容槽位。独立组装与 workflow 导出均使用 `rag/template_renderer.py`，不得改用空白 `Document()`、通用排版预设或两列表格模拟歌词双栏。保留模板页面尺寸、页边距、页眉横线、字体、主题、关系和真正的单双栏分节；歌曲标题、经文、两行结构表、歌词字号及段落配色按 [模板规则](references/template-rules.md) 执行。只替换旧曲目、旧日期、旧人员等样本内容，不覆盖模板原件或用户未保存修改。

修改导出器后运行模板保真回归；每次成品都在 WPS 逐页核对中文、双栏、配色、折行和结构表完整性。仅代码测试通过不能代替视觉验收；失败时修复后重新导出，不把旧版本当成最终文件。

先给组装预览和待补清单，按用户反馈局部修改。用户要求 Word 成品时，另存新 DOCX，不覆盖原始模板或 WPS 中未保存的用户修改；不自动上传、分享或写回 PCO。

优先在 WPS 核对实际中文显示、双栏、结构表宽度及颜色。用结构化读取核对文本、表格和颜色值作为补充，不把其他渲染器的缺字/空白页当作原件缺内容。交付文档前检查每页，未能核实版式时明确说明。

歌词双栏须逐首检查左右首个标题（通常为Verse与Chorus）及首行歌词处于同一水平线。分栏符放在右栏首标题段内，不另插空分栏段；不能仅凭分节和颜色正确就判定对齐通过。

新视觉验收按README的v5 `visual`结构记录实际应用、总页数、每页`blocks`归属、三首的实际`pages/lyrics_pages`及逐项样式观察；包括共用左边界、表格与歌词留白、主歌表格宽度协调及相邻乐段12pt留白（section_spacing）。跨页必须记录原因和排版尝试。不适用的基线或乐段间距项目在观察中说明，不用“全部正常”代替。具体规格见强制验收文档；旧版四项checks或v2/v3/v4不能替代新稿完整验收。辅助渲染器缺字或分页与WPS不同时保留诊断，不据此宣称视觉通过。

验收至少检查：五个位置齐全；前三首顺序和调正确；未提供的 BPM 均空白；经文原文和出处匹配；结构标记能对应实际歌词段；同段颜色一致；重复与编号未丢失；回应分支正确；结束结构有来源或待确认标记；无旧日期、人名、歌曲残留；无裁切、溢出或错栏。

组装确认只确认这份文档，不冒充选歌、定调试听、乐手 BPM 或祷告话语的独立确认。后续换歌、换调、改结构时重新核对受影响位置和复用引用。

### 完成后清理临时废弃文件

新版逐页版式检查通过后立即执行`artifact-finalize`，在同次操作中登记真实验收、核对哈希、替代旧导出、预演并删除本会话废弃DOCX/sources及登记预览；不等用户再提醒，不留到对话最后。制作和验收期间临时保留旧可用稿，通过后交付目录只保留一个当前最终DOCX和同名sources，以及必要口述稿、原始资料和审计。测试样稿不等于用户现场定稿。

开始生成时记录本次创建文件的明确路径清单；清理前逐个核对归属、是否已被最终成果替代、是否仍被会话/溯源引用。只删除清单内已废弃且不再被引用的文件，不按目录、通配符、时间或“临时”文件名批量删除。保留最终 DOCX、同名 sources、必要报告、原始模板、用户提供的原件、歌词/简谱/MP3、RAG 数据及原件快照、workflow 状态和仍被引用的试听缓存。WPS 打开或用户改过的文件先核对，不自动保存、覆盖或删除；归属不明则询问。

生成失败或版式未验收时保留诊断所需文件，不提前删除唯一可用版本。删除按当前环境权限执行；无权删除时明确报告待清理项，不宣称已清理。完成后简要说明保留的最终文件及清理结果。

`artifact-finalize`的`cleanup.checked_files`必须精确覆盖所有待删路径、登记哈希与实际`closed:true`观察；无待删文件也显式提交空列表，不能绕过收尾。缺项、仍打开、改过或有效引用会在首个删除前拦截；实际应用状态不能由代码证明，不得伪造。已有同哈希有效验收可用`use_existing_review:true`复用。新正式稿带`required_cleanup_version=1`，仅`artifact-review`/手动清理不能完成交付，已验收未收尾时也禁止新导出。交付前后`status`须见`finalization_valid=true`、`cleanup_remaining=[]`；阻塞时暂留并说明，不自动关闭或丢弃用户修改。报告顶部只维护当前结论，旧记录明确标为历史。
